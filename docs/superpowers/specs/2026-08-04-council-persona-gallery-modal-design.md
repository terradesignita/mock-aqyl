# Консилиум: модалка-галерея выбора участников

## Контекст и цель

Пользователь принёс внешний PRD-концепт (`Консилиум.md`, корень репозитория) — детальное описание продукта «Консилиум» с нуля, включая полноэкранную модалку выбора участников (12 фотокарточек, ч/б→цвет при выборе, лимит 3, toast на превышении). Фича «Консилиум» в этом репозитории уже полностью реализована и несколько раз отшлифована (`docs/superpowers/plans/2026-08-02-council-redesign.md` → `...-live-chat.md` → `...-visual-redesign.md`, последний коммит — вчера), поэтому этот документ **не** описывает продукт с нуля, а фиксирует точечные изменения к уже существующей реализации, согласованные с пользователем в диалоге (см. «Принятые решения» ниже).

Пользователь подтвердил три решения, определяющие масштаб:

1. **Персоны остаются вымышленными** («в духе X») — PRD настаивал на реальных публичных фигурах (Musk, Bezos, Huang...) с фото и реальными именами; это юридический/репутационный риск, который пользователь не готов принять. Текущий гардрейл в `src/data/council.ts` (вымышленное имя, реальный лидер только как стилевой ориентир, никогда источник цитаты) не меняется.
2. **Движок диалога остаётся детерминированным** (`buildOpeningMessages`/`buildFollowUpReplies` по архетипам и ключевым словам, тема — из `mockCards`) — PRD настаивал на 5-7-шаговых заскриптованных сценариях с фиксированными репликами. Пользователь предпочёл сохранить текущий движок: он уже работает на любом кейсе из базы, а не только на 2-3 заранее написанных.
3. **Только шаг выбора персон меняется на полноэкранную модалку-галерею** — это единственный визуальный элемент из PRD, который пользователь хочет перенести буквально.

**Не входит в этот документ** (явно отклонено или неприменимо после решений выше):
- реальные фото и ссылки Wikipedia/X/Website на персон — не подходят вымышленным персонам;
- заскриптованные пошаговые сценарии (`Step`/`response.json` из PRD §46-50) и «Completion State» (PRD §53) — нет фиксированной длины диалога;
- Drawer «Информация о консилиуме» (PRD §31) — избыточен, тема и состав уже всегда видны в `ConversationCover` над лентой сообщений;
- новая цветовая/типографическая система (PRD §57-63) — используем существующие токены проекта (`--color-*`, тени, скругления), чтобы не разъезжаться с остальным Insight Navigator;
- изменения шага 2 мастера (поиск кейса/темы) — остаётся как есть, без модалки.

## 1. Где меняется UI

Модалка заменяет **только** шаг `"contacts"` внутри `NewCouncilPanel` (`src/routes/council.tsx`). Сегодня это блок кода между строками ~272-375 (условие `step === "contacts"` рендерит инлайн-карточку прямо в основной колонке). Шаг `"topic"` (поиск кейса) не трогаем: он остаётся инлайн-панелью, без модалки, — так и сохраняется движок на `mockCards` (решение 2 выше).

Триггер открытия — тот же, что сегодня запускает мастер: кнопка «Создать совет» в сайдбаре (`CouncilPage`, `onClick={() => { setCreating(true); setActiveId(null); }}`) и кнопка «Новый консилиум»/аналог. Разница: вместо инлайн-рендера шага 1 в `<main>`, при `creating && step === "contacts"` открывается `PersonaGalleryModal` (Dialog) поверх текущего состояния экрана (сайдбар + предыдущий чат остаются видны и размыты на фоне — как в PRD §7).

## 2. Новый компонент `PersonaGalleryModal`

Строится на уже используемом `@/components/ui/dialog` (Radix `Dialog`, зависимость уже установлена — новых пакетов не добавляем). Файл: тот же `src/routes/council.tsx` (компонент рядом с `NewCouncilPanel`, не отдельный файл — по объёму сопоставим с существующим `PersonaPicker`, выносить в отдельный модуль незачем).

```tsx
function PersonaGalleryModal({
  open,
  selected,
  onChange,
  onConfirm,
  onClose,
}: {
  open: boolean;
  selected: string[];
  onChange: (ids: string[]) => void;
  onConfirm: () => void;
  onClose: () => void;
}) { /* ... */ }
```

Размер: `max-w-[1400px] min-w-[1100px] w-[90vw] h-[90vh]` на десктопе (`Dialog` уже центрирует и затемняет фон — совпадает с PRD §7-8 без доп. кода). Скругление модалки — существующий семантический токен `rounded-modal` (`--radius-modal`, `src/styles.css:38`, фактически 14px при базовом `--radius: 0.5rem`), а не буквальные «24px» из PRD §8: токен уже существует именно для модалок и просто не использован ни в одном компоненте — вводить рядом другое магическое число для одной вьюхи значило бы завести два конкурирующих определения «скругления модалки» в одной кодовой базе.

Содержимое сверху вниз:
- заголовок «Соберите консилиум» + подзаголовок «Выберите от одного до трёх участников» (PRD §10, текст переносится буквально — он нейтрален и не зависит от решений 1-3);
- счётчик «Выбрано N из 3» (переиспользует текущий текст-паттерн `personaIds.length}/{MAX_PERSONAS`, только с этой формулировкой вместо `N/3`);
- предупреждение о низком шансе спора (`hasLikelyDisagreement`) — переносится из текущего шага 1 без изменений, это полезная фича сверх PRD, не противоречит ему;
- ссылка «Подобрать автоматически» (`pickDefaultTrio`) — переносится без изменений;
- сетка 4×3 карточек (см. §3);
- фиксированная кнопка «Создать совет» внизу — `disabled` при `selected.length === 0`, при клике вызывает `onConfirm` (переводит мастер на шаг `"topic"`, модалка закрывается).

Закрытие без подтверждения — кнопка «Отмена» рядом с «Создать совет», клик по оверлею и `Esc` (все три — стандартное поведение Radix `Dialog`, ничего не пишем руками) вызывают `onClose`, что сбрасывает `creating` в `false` и возвращает на предыдущий экран (`SessionsOverview` или прежний открытый чат) — как в PRD §7 («закрытие модалки возвращает пользователя обратно к предыдущему чату»).

Поиска по персонам в самой модалке **нет** — PRD описывает статичную галерею 12 карточек без поля поиска (в отличие от текущего `PersonaPicker` в сайдбаре, который поиск сохраняет, он не меняется). При 12 персонах и сетке 4×3 все карточки видны без скролла на 90vh — поиск был бы решением несуществующей проблемы.

## 3. Карточка персоны в сетке

Переиспользует существующие данные (`CouncilPersona.hex/darkHex/tag/role/inspiredBy`) и существующий `PersonaAvatar` — новых полей в `council.ts` не добавляется.

```tsx
function GalleryCard({ persona, selected, disabled, onToggle }: {
  persona: CouncilPersona;
  selected: boolean;
  disabled: boolean;
  onToggle: () => void;
}) {
  return (
    <button
      type="button"
      onClick={onToggle}
      disabled={disabled}
      aria-pressed={selected}
      style={personaColorVars(persona)}
      className={cn(
        "group relative flex flex-col items-center gap-2 rounded-2xl border p-4 text-center transition-[transform,box-shadow,border-color,opacity] duration-200",
        selected
          ? cn("-translate-y-0.5 border-primary shadow-md", PERSONA_BORDER_CLASS)
          : "border-border hover:border-primary/30 hover:shadow-sm",
        disabled && "opacity-40",
      )}
    >
      {selected && (
        <span className="absolute right-3 top-3 grid h-5 w-5 place-items-center rounded-full bg-primary text-primary-foreground">
          <Check className="h-3 w-3" />
        </span>
      )}
      <PersonaAvatar
        initials={persona.initials}
        size="lg"
        style={{ backgroundColor: persona.hex }}
        className={cn(
          "transition-[filter,transform] duration-200 group-hover:scale-105",
          !selected && "grayscale saturate-[.35]",
        )}
      />
      <span className="text-sm font-semibold text-card-foreground">{persona.name}</span>
      <PersonaTag tag={persona.tag} hex={persona.hex} />
      <span className="line-clamp-2 text-xs text-muted-foreground">
        {persona.role} · в духе {persona.inspiredBy}
      </span>
    </button>
  );
}
```

Ч/б → цвет (PRD §15) реализуется CSS-фильтром на существующем цветном `PersonaAvatar` (`grayscale saturate-[.35]` → убирается при выборе), а не подменой изображения — карточка не «прыгает» размером, ровно как требует PRD §15/17 («размер фотографии не меняется», «карточка остаётся на своём месте»), и не нужен второй ассет на персону.

Лимит 3 и disabled-состояние — та же логика, что уже есть в `togglePersona`/`PersonaPicker.toggle` (переносится без изменений, включая toast):

```ts
const toggle = (id: string) => {
  if (selected.includes(id)) return onChange(selected.filter((x) => x !== id));
  if (selected.length >= MAX_PERSONAS) {
    toast.error("Можно выбрать не более трёх участников.");
    return;
  }
  onChange([...selected, id]);
};
```

Текст toast — буквально из PRD §18.

## 4. Тестирование

Нечего покрывать новыми unit-тестами в `council.test.ts` — весь перенесённый функционал (`toggle`, лимит, `pickDefaultTrio`, `hasLikelyDisagreement`) уже покрыт существующими тестами данных, а сама модалка — чистый UI-компонент без новой бизнес-логики. Один runnable-чек: ручная браузерная проверка (Playwright MCP, уже используется в этой сессии для прошлых council-тасков) — открыть модалку, выбрать 3 персоны, попытаться выбрать 4-ю (toast), снять выбор одной, подтвердить переход на шаг темы, обе темы (light/dark).

## Принятые решения (лог диалога)

1. Реальные имена vs вымышленные персоны → **вымышленные, без изменений** (юридический риск для бизнеса).
2. Заскриптованные сценарии vs текущий детерминированный движок → **текущий движок остаётся**.
3. Компактный инлайн-пикер vs большая модалка-галерея → **большая модалка по PRD**, но только на шаге выбора персон; шаг выбора темы/кейса не меняется.
