# Консилиум как живой групповой чат — спецификация

Дата: 2026-08-04

## Контекст и источник

Пользователь принёс внешний ТЗ «Моковый веб-прототип ИИ-консилиума» (сгенерирован отдельно, не написан вручную). ТЗ описывает мессенджер-формат: пользователь собирает до 3 участников, обсуждает кейс в групповом чате, участники отвечают с задержкой/индикатором печати, иногда реагируют друг на друга, доступны быстрые ответы.

Это заменяет предыдущий подход (карта согласия/конфликта без синтеза, документ `docs/Смоделированный_клиентский_путь_Консилиума.md` — удалён, не отражает финальное направление) и текущую реализацию (`Вердикт совета` — синтез + открытые вопросы + теги согласия).

## Решённые вопросы

1. **Имена участников** — вымышленные «в духе», как уже сделано в проекте (`COUNCIL_PERSONAS`, `inspiredBy`). Реальные имена (Маск, Джобс, Безос, Рахимбаев и т.д.) из исходного ТЗ не используются — риск атрибуции вымышленных цитат реальным живым людям (особенно для Айдына Рахимбаева — гораздо менее публичная фигура, чем глобальные миллиардеры, выше риск репутационного вреда).
2. **Формат продукта** — живой групповой чат из ТЗ, а не карта согласия/конфликта.
3. **Панель вердикта** — убирается полностью, включая её ресайз/сворачивание/копирование (добавлены в этой же сессии ранее). Согласие/спор видны прямо в переписке, отдельного синтеза нет.
4. **Глубина проработки мессенджера** — проверено визуальным сравнением (два макета: минимальный чат vs полноценный мессенджер), выбран **полноценный**: таймштампы на каждом сообщении, статус «Прочитано ✓✓» у сообщений пользователя, персона может отправить 2 коротких сообщения подряд вместо одного, явная подпись «отвечает N» у реплики-реакции, индикатор «печатает…», статус «на связи» в шапке чата. Это отменяет пункт «вне рамок» из более ранней черновой версии этого документа — теперь всё перечисленное **в рамках**.

## Что переносится из ТЗ без изменений

- Тайминги: typing delay 600–1400мс, message delay 1000–2500мс (§9 ТЗ).
- Быстрые ответы над полем ввода (§10 ТЗ): «Какие главные риски?», «Что бы вы сделали первым?», «Вы согласны друг с другом?», «Дайте конкретный план», «Продолжить».
- Механика реакции одного участника на реплику другого (§13 ТЗ) — как опциональный, а не обязательный элемент каждого хода.
- Требование к длине реплик: 1–3 предложения, 10–70 слов (§9 ТЗ) — текущий `buildPersonaTake` уже в основном укладывается, точечная правка длины по месту.

## Что адаптируется под существующий стек

Проект — Vite + TanStack Router + React 19 + Tailwind v4, не Next.js. Ниже — что из ТЗ **не** переносится, и чем заменяется.

| Из ТЗ | Не переносим, потому что | Вместо этого |
|---|---|---|
| Next.js / Zustand / отдельный JSON-движок сценариев | В проекте уже есть React/Vite и детерминированные функции в `src/data/council.ts` | Те же паттерны: чистые функции, без нового рантайма |
| Фиксированное меню из 3–5 сценариев (Экран 3 ТЗ) | В проекте уже есть гибкий выбор кейса из библиотеки (`mockCards`) | Кейс — это и есть тема обсуждения, отдельный экран выбора сценария не нужен |
| Отдельный «Экран информации о консилиуме» (drawer) | В сайдбаре уже есть блок «Совет» + «Изменить состав» (§15 ТЗ описывает то же самое) | Существующий блок в сайдбаре, без нового drawer |
| «Экран истории» с отдельным списком чатов | Список сессий в сайдбаре уже это делает | Существующий список, только превью карточки меняется с синтеза на последнее сообщение |
| Новый набор из 12 личностей | В проекте уже 12 вымышленных персон с цветами/инициалами/стилем | `COUNCIL_PERSONAS` без изменений |

## Модель данных (`src/data/council.ts`)

### Новый тип сообщения

```ts
export interface CouncilChatMessage {
  id: string;
  /** "user" или id персоны из COUNCIL_PERSONAS */
  author: "user" | string;
  text: string;
  /** Время создания, "ЧЧ:ММ" — тот же паттерн, что уже есть в NotebookChat.tsx (`now()`). */
  time: string;
  /** id персоны, на чью реплику это реакция — рендерится как подпись "отвечает <Имя>". */
  replyTo?: string;
}
```

**Статус прочтения** («Прочитано ✓✓» у сообщений пользователя) — это НЕ поле в данных, а производное состояние UI: как только для сообщения пользователя сгенерирован и начал проигрываться ответный каскад (см. ниже), оно считается прочитанным. Хранить `read: boolean` в `CouncilSession` не нужно — после перезагрузки страницы весь каскад уже завершён, значит все сообщения пользователя, у которых есть последующий ответ персоны, автоматически «прочитаны».

**Серия из нескольких сообщений подряд** — не отдельное поле, а естественное следствие того, что и `buildOpeningMessages`, и `buildFollowUpReplies` возвращают **массив** сообщений: два подряд идущих сообщения с одинаковым `author` — это и есть серия. UI группирует подряд идущие сообщения одного автора визуально (аватар/имя показываются один раз на серию, не на каждое сообщение).

### `CouncilSession` — миграция схемы

`followUps: string[]` заменяется на `messages: CouncilChatMessage[]`. Это несовместимое изменение схемы — по образцу уже существующего в кодовой базе прецедента («Bump council-sessions storage key to invalidate incompatible pre-branch data»), ключ `useLocalStorage` в `useCouncilSessions` меняется с `biaqyl:council-sessions:v2` на `biaqyl:council-sessions:v3`, `SEED_COUNCIL_SESSIONS` переписывается под новую схему.

### Новые функции, взамен `buildVerdict`/`buildAgreements`

```ts
/** Стартовые реплики при создании сессии: одна короткая реплика на персону +
 *  опционально одна реакция несогласия, если среди выбранных персон есть
 *  явная "оптимист/скептик" пара. */
function buildOpeningMessages(personaIds: string[], topic: CouncilTopic): CouncilChatMessage[];

/** Ответы на follow-up: 1-2 персоны отвечают (не обязательно все), выбор —
 *  по простому keyword-совпадению с текстом вопроса, тем же способом, что
 *  buildFollowUpReply у советника и buildAnswer в NotebookChat. */
function buildFollowUpReplies(
  personaIds: string[],
  topic: CouncilTopic,
  followUpText: string,
): CouncilChatMessage[];
```

`buildPersonaTake` меняет тип возврата с `string` на `string[]` (1-2 короткие реплики вместо одного абзаца). Большинство из 12 шаблонов уже состоят из двух предложений («Смело: {insight} Если это не меняет правила игры…») — механически разбиваются на два элемента массива по границе предложения, без переписывания контента с нуля.

**"Оптимист/скептик" пара для реакции несогласия** — статичные множества (аналог `RISK_PERSONAS`, который уже есть в файле):

```ts
const BULLISH = new Set(["founder", "product", "platform"]);
const SKEPTICAL = new Set(["contrarian", "competitor", "resilience"]);
```

Если среди выбранных 3 персон есть хотя бы одна из каждого множества — скептик получает вторую реплику с `replyTo: <id оптимиста>`, явно ссылающуюся на его позицию. Если пары нет — реакции нет (не подделываем несогласие, если состав совета его не подразумевает).

**Быстрые ответы** — статичный список вместо `PERSONA_QUESTIONS`-as-открытые-вопросы:

```ts
const QUICK_REPLIES = [
  "Какие главные риски?",
  "Что бы вы сделали первым?",
  "Вы согласны друг с другом?",
  "Дайте конкретный план",
];
```

## Интерфейс (`src/routes/council.tsx`)

### `NewCouncilPanel` — порядок меняется на «сначала люди, потом тема» (как WhatsApp/Telegram «Новая группа»)

Сейчас: выбрать кейс → персоны подбираются автоматически (по хэшу) → опционально поправить состав. Пользователь явно попросил порядок как в мессенджере: сначала выбираешь до 3 «контактов», потом даёшь группе тему.

Новый порядок — два шага внутри той же карточки (`space-y-6 rounded-2xl border ... shadow-soft`, уже добавлена ранее в этой сессии):

**Шаг 1 — «Кто в совете».** Список всех 12 персон как основной контент экрана (не свёрнутый чип-список, а полноценная раскладка с аватаром/именем/ролью на каждую — переиспользуем разметку строки из существующего `PersonaPicker`), поиск по имени/стилю сверху, счётчик «Выбрано X из 3» (по образцу текущего «Совет (N/3)»). Клик по персоне — тоггл выбора, как чекбокс. Кнопка «Далее» активна после выбора хотя бы одной персоны. Автоподбор по хэшу (`suggestPersonas`) для этого экрана **убирается** — раз пользователь выбирает вручную, как в мессенджере, автоугадывание вводило бы в заблуждение (можно оставить `suggestPersonas` как внутреннюю функцию для других нужд, но не вызывать её на этом шаге).

**Шаг 2 — «О чём поговорим».** Существующий поиск кейса (`Найдите кейс по названию`) без изменений. Выбор кейса + нажатие «Начать совет» создаёт сессию с персонами из шага 1 и генерирует `buildOpeningMessages`.

Переключение между шагами — простое `step: "contacts" | "topic"` состояние в компоненте, без роутинга. Кнопка «Назад» на шаге 2 возвращает на шаг 1 с сохранённым выбором персон.

«Изменить состав» у уже активной сессии (в сайдбаре) не меняется по механике — открывает тот же список персон инлайн, что и раньше, никакого нового шага не добавляется, потому что там персоны не выбираются «с нуля».

### Убирается полностью

`VerdictPanel` и всё его окружение: компонент, `verdictWidth`/`startVerdictResize`/`showVerdict`/`verdictRestoreRef`/`verdictPanelRef`, плавающая кнопка возврата, ручка ресайза, `formatVerdictForCopy` и кнопка копирования, `pendingFollowUp`/`submitFollowUp` (текущая реализация «раздумья» — заменяется механикой реального чата ниже).

### `SessionView` — переписывается в групповой чат

- **Шапка чата**: `AvatarStack` (уже есть) + «N участников» + название кейса. Отдельная от блока «Совет» в сайдбаре — тот остаётся как есть для управления составом.
- **Лента сообщений**: `session.messages` рендерится как цепочка `MessageBubble` (`variant="user"` для пользователя справа, `variant="entity"` с аватаром/именем персоны слева — обе разновидности уже существуют и используются).
- **Индикатор печати + задержка появления**: реализуется по тому же паттерну, что уже есть в `AdvisorFlow.runThinking` (каскад `window.setTimeout`, инкрементальный показ по индексу) — переиспользуем технику, не изобретаем новую. Анимация проигрывается только для сообщений, добавленных за текущий визит в сессию (снэпшот `session.messages.length` при монтировании); всё, что уже было сохранено раньше, показывается сразу, без повторного «печатания» при каждом открытии сессии.
- **Быстрые ответы**: ряд чипов над полем ввода из `QUICK_REPLIES`, клик = отправка как обычного сообщения.
- **Поле ввода**: как сейчас, дизейблится на время проигрывания каскада ответов.

### `SessionsOverview` / карточка сессии

Превью в карточке (`verdict.synthesis`, потому что `buildVerdict` удалён) заменяется на текст последнего сообщения: `session.messages.at(-1)?.text ?? session.topic.summary`.

### `useAppState.ts`

`addFollowUp(id, text)` заменяется на `addMessages(id, messages: CouncilChatMessage[])` — добавляет пачкой (сообщение пользователя + ответы персон одним вызовом), т.к. один ход теперь может добавлять больше одного сообщения.

## Явно вне рамок этой версии

- Полный граф попарных реакций между всеми комбинациями персон — только одна оппортунистическая реакция несогласия при создании сессии, не на каждый ход.
- Отдельный modal/drawer «Экран информации о консилиуме» — переиспользуем существующий блок в сайдбаре.
- Имитация ошибки/сбоя участника (§17 ТЗ, Error simulation).
- Персистентность/восстановление состояния "печатает" при обновлении страницы посреди каскада — при перезагрузке все сохранённые сообщения просто показываются сразу.

## Тестирование

- Существующие тесты `council.test.ts` (гвардрейл на утечку реальных имён, `suggestPersonas`, `buildPersonaTake`) обновляются под новые функции: `buildOpeningMessages`, `buildFollowUpReplies` — тот же гвардрейл-тест на реальные имена должен покрывать и новые функции.
- `buildVerdict`/`buildAgreements`-тесты удаляются вместе с функциями.
- Ручная проверка через Playwright: создание сессии → видно каскадное появление реплик с индикатором печати → follow-up → быстрые ответы → реакция несогласия при подходящем составе персон → превью в `SessionsOverview` показывает последнее сообщение.
