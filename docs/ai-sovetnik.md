# AI-советник — обзор для инженера

Дата: 2026-08-02

## Что это и где живёт

AI-советник — второй режим строки поиска на главной странице (не отдельный раздел). Пользователь переключает тумблер «Режим AI-советника» в `SearchPanel` и вместо обычного поиска по кейсам получает диалоговый мастер принятия управленческого решения.

Точки входа:

| Файл | Роль |
|---|---|
| `src/components/SearchPanel.tsx` | тумблер `aria-label="Режим AI-советника"`, переключает режим на главной |
| `src/routes/index.tsx` | рендерит `<AdvisorFlow query={advisorQuery} onReset={...} />`, когда режим включён |
| `src/components/advisor/AdvisorFlow.tsx` | сам мастер — 4 стадии: Уточнение → Понимание → Анализ → Рекомендация |
| `src/components/advisor/ClarifyBlock.tsx` | экран уточняющих вопросов |
| `src/components/advisor/UnderstandingCard.tsx` | экран «Вот как я понял вашу ситуацию» |
| `src/components/advisor/AdvisorAnswer.tsx` | рендер итоговой рекомендации |
| `src/data/advisor.ts` (629 строк) | вся бизнес-логика: классификация, вопросы, сборка ответа |

Не путать с разделом «Консилиум» (`src/routes/council.tsx`, `src/data/council.ts`) — это отдельная, никак не связанная фича с симуляцией совета из персон-архетипов.

## Бизнес-ценность

AI-советник — не поиск, а продукт с отдельным ценностным предложением: пользователь описывает управленческую дилемму («брать ли партнёра», «продавать ли долю», «выходить ли на новый рынок») и получает не список документов, а структурированную рекомендацию, подкреплённую конкретным прецедентом из базы кейсов.

Прототип нужен, чтобы:

- показать саму идею продукта инвесторам/стейкхолдерам и на юзер-тестах до того, как вкладываться в реальный LLM/RAG-пайплайн;
- провалидировать UX-поток решения (уточнение → понимание → рекомендация → follow-up) — если пользователи спотыкаются на этом сценарии, дешевле это найти сейчас, чем после интеграции платной модели;
- продемонстрировать связку «рекомендация → конкретный кейс с источником и цитатой» — то, что отличает продукт от обычного чат-бота.

## Критерии успеха прототипа

Прототип оправдывает инвестиции в реальный LLM/RAG, если на юзер-тестах/демо подтверждается:

- пользователи проходят весь поток (уточнение → понимание → рекомендация), не бросая на середине;
- рекомендация воспринимается как релевантная их ситуации, а не как общий сгенерированный текст;
- пользователи задают follow-up-вопросы — значит, доверяют формату достаточно, чтобы продолжать диалог, а не уходят сразу после первого ответа.

Если этих сигналов нет, стоит доработать сам сценарий (порядок вопросов, формат рекомендации), прежде чем вкладываться в интеграцию модели — mock дешевле итерировать, чем production-пайплайн.

### Критерии остановки

Обратный сигнал — сценарий не заходит, и тянуть его дальше не стоит:

- пользователи массово бросают на экране уточняющих вопросов, не доходя до рекомендации;
- рекомендация регулярно называется нерелевантной или «водой» независимо от того, как переформулирован запрос;
- никто не задаёт follow-up — рекомендацию воспринимают как финальный ответ, не как повод для диалога.

В этом случае проблема, скорее всего, в самом сценарии (порядок шагов, формат вывода), а не в том, что ответы moковые — заменять на реальный LLM в такой ситуации рано: он не чинит проблему UX, а просто делает её дороже воспроизводить.

## Как это работает сейчас (всё на моках)

Вся логика в `src/data/advisor.ts` — **детерминированная, без LLM и без бэкенда**. Комментарий в начале файла фиксирует это как сознательное решение:

> Моковая модель AI-советника BI AQYL (ТЗ v1.0). Вся логика детерминированная — точка подключения реального LLM одна: заменить `buildAnswer`/`classify` на серверную функцию, интерфейс не меняется.

Поток:

1. **Классификация запроса.** `isManagerialQuery()` отсекает обычные поисковые запросы («найди документ») от управленческих. `classify()` определяет тип дилеммы по ключевым словам (партнёрство, продажа доли, выход на рынок, масштабирование, инвестиции, оргмодель) — простой матчинг по подстрокам, без ИИ.
2. **Уточняющие вопросы** (`ClarifyBlock`). Для каждого типа дилеммы — заготовленный набор вопросов с вариантами ответов. Детально проработан только тип «партнёрство» (`PARTNERSHIP_QUESTIONS`), остальные используют упрощённый общий набор (`GENERIC_QUESTIONS`).
3. **Экран понимания** (`UnderstandingCard`). `buildUnderstanding()` собирает текстовое резюме из ответов пользователя, можно вернуться и поправить.
4. **Имитация анализа.** `runThinking()` последовательно подсвечивает фиксированный список шагов (`THINKING_STEPS`) с задержкой ~420мс каждый — реального вычисления не происходит, это чисто визуальный эффект «модель думает».
5. **Рекомендация** (`AdvisorAnswer`). `buildAnswer()` возвращает захардкоженный объект: вердикт, аргументы, таблицу сценариев (скорость/контроль/риск), условия сделки, риски, «что может изменить рекомендацию», источники с цитатами. Единственный кейс в базе — Dr. John's Products (учебный кейс HBS), зашит целиком.
6. **Follow-up.** `buildFollowUpReply()` матчит вопрос пользователя по ключевым словам и возвращает один из заготовленных шаблонных ответов.

Состояние диалога — локальный `useState`, никуда не персистится.

## Известные ограничения

### ⚠️ Бизнес-риск — закрыть до любого внешнего показа

`buildAnswer()` всегда отдаёт полную уверенную рекомендацию, даже когда `evidenceLevel === "недостаточно данных"` — раздела «честного отказа» нет. Если прототип в этом виде попадёт к реальным пользователям (демо клиенту, ранний доступ), система будет выглядеть как уверенно рекомендующая решение там, где данных для этого недостаточно. Для продукта, который позиционируется как инструмент поддержки управленческих решений, это репутационный риск, а не рядовой баг — не откладывать вместе с техдолгом ниже.

### ⚠️ Ограничение демо — единственный кейс в базе

В базе рекомендаций зашит только один кейс — Dr. John's Products. Пока это так, сценарий убедительно работает только на дилеммах, для которых он релевантен. Если на юзер-тесте или у клиента прозвучит вопрос про другую ситуацию, рекомендация всё равно привяжется к тому же кейсу и будет выглядеть неубедительно или притянутой за уши. Перед любым показом за пределами команды — либо предупреждать тестирующего/демонстрирующего держаться сценария вокруг этого кейса, либо завести ещё 1–2 кейса под другие типы дилемм.

**Требование на будущее.** Когда подбор кейса станет реальным retrieval по базе (а не единственным зашитым кейсом), нужно явно предусмотреть ситуацию «подходящего кейса нет» — `buildAnswer()` не должен принудительно привязывать рекомендацию к ближайшему, но нерелевантному кейсу. Нужен отдельный исход: рекомендация без привязки к прецеденту или прямое сообщение, что подходящего кейса в базе не нашлось, вместо того чтобы выдавать её как будто кейс подошёл. Это тот же принцип, что и с «честным отказом» при недостатке данных выше — тот же класс проблемы, только по оси «есть ли релевантный кейс», а не «достаточно ли данных».

### ✅ Исправлено — сброс прогресса при правке верхней строки поиска

При живом краш-тесте (02.08.2026) обнаружилось: любое изменение текста в строке поиска над `AdvisorFlow` — даже одна случайная клавиша — мгновенно уничтожало весь прогресс мастера (ответы на вопросы, экран понимания), потому что `onQueryChange` в `src/routes/index.tsx` безусловно вызывал `setAdvisorQuery(null)` на каждое изменение. Кнопка «Назад» браузера тут была ни при чём — начальная гипотеза оказалась неверной, реальная причина обнаружилась только на живом тесте. Пофикшено: `onQueryChange` больше не трогает `advisorQuery` — сброс происходит только через явный `onReset` или отправку новой формулировки (`submit()`), а не на каждый ввод в поле.

### Техдолг (зафиксирован в `HANDOFF.md`, можно копить до реальной LLM-интеграции)

- Follow-up не пересчитывает реальный ответ на основе текста вопроса — только выбирает шаблон по ключевым словам.
- Значение «Пока неизвестно» может протечь как литеральная строка `__unknown` в текст экрана понимания ситуации.
- Уточняющие вопросы в `ClarifyBlock` статичные, с фиксированным числом полей на экран — см. следующий раздел: это расхождение с задуманным поведением, а не просто временное упрощение.
- `buildAnswer()` физически игнорирует тип дилеммы: для любого типа, кроме `partnership`/`build_or_partner`, рекомендация всё равно звучит как про партнёрство и доли — см. «Полная карта точек интеграции LLM» ниже, пункт 7.

## Как должны работать уточняющие вопросы (уточнено в переписке с инженером, 02.08.2026)

Текущая реализация `ClarifyBlock` — статичные наборы вопросов на тип дилеммы (`PARTNERSHIP_QUESTIONS`, `GENERIC_QUESTIONS`) с фиксированным числом полей. Это упрощение из-за сроков, не финальное поведение. По замыслу:

- Вопросы генерируются на основе исходного запроса пользователя, а не берутся из статичного набора — по аналогии с тем, как сам Клод в харнессе Claude Code задаёт уточняющие вопросы по контексту, а не по шаблону.
- Количество вопросов на экране не фиксировано — 3–5 в зависимости от того, что нужно уточнить.
- Количество экранов уточнения тоже не фиксировано, но ограничено сверху — не более 5 экранов.
- Динамическая генерация вопросов тоже расходует токены — учитывать отдельно от стоимости генерации самой рекомендации при оценке затрат на реальную интеграцию.

Если по этому поведению возникают новые вопросы до того, как оно формализовано отдельным ТЗ, — уточнять сразу, не откладывать до следующего цикла работ.

## Полная карта точек интеграции LLM

Порядок ниже — это порядок вызовов в `AdvisorFlow.tsx` (`useMemo`/обработчики, строки 94–135). Внедрять стоит сверху вниз: результат каждого шага идёт на вход следующему, поэтому начинать с конца (сразу чинить `buildAnswer`) бессмысленно — он всё равно получит на входе тот же ограниченный `selection`, пока не заменены шаги 2–3.

**1. `isManagerialQuery(query)`** — `advisor.ts:316`, вызов в `AdvisorFlow.tsx:135`.
Сейчас: длина запроса ≥12 символов и не начинается с «найди»/«покажи»/«материал»/... (жёсткий список префиксов).
LLM-версия: классификация intent — это управленческая дилемма или обычный поиск по базе. Вход: текст запроса. Выход: булево (+ опционально уверенность).
Приоритет: низкий — эвристика редко ошибается на реальных формулировках, менять смысла нет, пока нет конкретных фейлов.

**2. `classify(query)`** — `advisor.ts:324`, вызов в `AdvisorFlow.tsx:94`.
Сейчас: перебор `RULES` — по вхождению ключевых слов возвращает один из 7 фиксированных `DilemmaType` (`partnership`, `build_or_partner`, `sale`, `new_market`, `scaling`, `investment`, `org_model`), иначе молча возвращает дефолт `build_or_partner`.
LLM-версия: классификация типа дилеммы по смыслу запроса, а не по ключевым словам — должна ловить перефразированные формулировки без «партн»/«прода»/«рынок» и т.п. Вход: текст запроса. Выход: один из `DILEMMAS` (и явный сигнал, если ни один тип не подходит — сейчас эта ситуация скрыта дефолтом).
Приоритет: высокий — уже отмечен в коде как официальная точка интеграции. Влияет на все шаги 3–7.

**3. Генерация уточняющих вопросов** — сейчас `DILEMMAS[type].questions`, статичные наборы `PARTNERSHIP_QUESTIONS`/`SALE_QUESTIONS`/`MARKET_QUESTIONS`/`GENERIC_QUESTIONS` (`advisor.ts:84–255`).
Подробное описание задуманного поведения — в разделе «Как должны работать уточняющие вопросы» выше. Технически: результат должен возвращаться в том же формате `ClarifyQuestion[]` (с полем `triggeredBy` для адаптивных вопросов вроде `exclusive_scope`), чтобы `visibleQuestions()` и `ClarifyBlock` не пришлось переписывать логику показа — только источник данных.
Приоритет: высокий — первое содержательное, что видит пользователь после выбора кейса.

**4. `extractKnown(query)`** — `advisor.ts:331`, вызов в `AdvisorFlow.tsx:95`.
Сейчас: 4 regex-паттерна вытаскивают из текста запроса одну из 4 заранее заданных фраз («речь о собственном продукте компании» и т.д.); если ни один не сработал — заглушка «управленческая ситуация без явных параметров в формулировке».
LLM-версия: извлечение реальных фактов из свободного текста запроса вместо подгонки под 4 шаблона. Вход: текст запроса. Выход: список строк-фактов (или структурированный объект, если так будет удобнее для шага 6).
Приоритет: средний — просадка заметна на длинных или нетипичных запросах, где regex ничего не находит и выдаёт пустую заглушку.

**5. `contextIsSufficient(dilemma, selection)`** — `advisor.ts:360`, вызов в `AdvisorFlow.tsx:105`.
Сейчас: механическая проверка — на все обязательные вопросы есть выбор варианта или свой текст.
LLM не нужен как отдельный вызов: это дешёвый и предсказуемый гейт, разумно оставить правилом. Но как только вопросы шага 3 станут динамическими по числу и составу, этой функции нужно знать, какие из сгенерированных вопросов обязательны, — это должен передавать сам LLM-вызов шага 3, а не выводиться заново отдельной логикой.
Приоритет: низкий как самостоятельная точка, зависит от формата ответа шага 3.

**6. `buildUnderstanding(dilemma, selection, query)`** — `advisor.ts:369`, вызов в `AdvisorFlow.tsx:106`.
Сейчас: для `partnership`/`build_or_partner` — вручную написанная цепочка условных фраз под конкретные id вопросов (`proof`, `partner_gives`, `partner_wants`, `priority`, `exclusive_scope`); для всех остальных 5 типов — общий цикл `"{вопрос} — {выбранные варианты}"` без связного текста.
LLM-версия: связное резюме «вот как я понял вашу ситуацию» из выбранных ответов и текста пользователя, одинаково качественное для любого типа дилеммы. Вход: dilemma + selection + query. Выход: строка.
Приоритет: высокий — сейчас это самое заметное место, где качество явно проседает вне сценария «партнёрство».

**7. `buildAnswer(dilemma, selection)`** — `advisor.ts:426`, вызов в `AdvisorFlow.tsx:107`.
⚠️ Важное ограничение, не описанное в предыдущих версиях документа: функция физически игнорирует `dilemma.type` в содержимом ответа. Все проверки внутри (`has("proof", ...)`, `has("partner_wants", ...)`, `selection.choices["priority"]`) читают id вопросов, которые существуют только в `PARTNERSHIP_QUESTIONS`. Для любого другого типа дилеммы (`sale`, `new_market`, `scaling`, `investment`, `org_model`) эти id в `selection.choices` никогда не заполнятся — и `buildAnswer` вернёт рекомендацию, дословно написанную под партнёрство («партнёр», «доля», «эксклюзивность»), даже если пользователь спрашивал про продажу доли или выход на рынок. **Демонстрировать прототип сейчас можно только на дилеммах типа «партнёрство» — на любом другом типе текст рекомендации будет откровенно не в тему.**
LLM-версия: сборка полной рекомендации (вердикт, аргументы, сценарии, условия, риски, источники) на основе типа дилеммы и ответов на уточняющие вопросы, плюс в перспективе — retrieval по базе кейсов вместо единственного зашитого `DR_JOHNS` (см. «Требование на будущее» выше). Вход: dilemma + selection (+ найденный кейс, когда появится retrieval). Выход: `Answer` — структура уже описывает всё нужное, менять её не требуется.
Приоритет: критический — и как основная точка интеграции LLM, и как самый заметный баг демо-сценария ещё до неё.

**8. `buildFollowUpReply(question, answer)`** — `advisor.ts:598`, вызов в `AdvisorFlow.tsx:122`.
Сейчас: 4 regex-паттерна по ключевым словам вопроса («объём/гаранти», «эксклюзив/сегмент», «сценар/окно/срок/месяц», «риск»), иначе — универсальная заглушка.
LLM-версия: реальный ответ на follow-up с учётом текста вопроса и уже сформированной рекомендации, вместо выбора одного из 4 шаблонов. Вход: question + answer. Выход: строка.
Приоритет: средний — заметно, когда follow-up не попадает ни в один из 4 паттернов.

**`THINKING_STEPS`** (`advisor.ts:617`) — не точка интеграции LLM, а чисто визуальный список шагов с фиксированной задержкой 420мс каждый (`AdvisorFlow.tsx:129–132`). Когда шаги 2–7 станут реальными LLM/API-вызовами, эту анимацию стоит привязать к фактическому прогрессу или заменить на стриминг — иначе экран будет показывать шаги, которые не соответствуют тому, что происходит на самом деле.

`Answer` и структура `Understanding` рассчитаны так, чтобы `UnderstandingCard`/`AdvisorAnswer` не пришлось переписывать. А вот `ClarifyBlock` и его степпер, скорее всего, потребуют правок под переменное число вопросов и экранов — сейчас они рассчитаны на фиксированный набор на тип дилеммы.

Перед переходом на реальную модель стоит закрыть ограничения из раздела «Известные ограничения» — иначе бизнес-риск (нет честного отказа) перейдёт в production вместе с остальным техдолгом.

### Находки для инженера (с привязкой к коду)

**1. ✅ Исправлено — одиночный/множественный выбор.** `priority` (`advisor.ts`) переведён на `multi: true` — совпадает с ТЗ §8 и customer journey, где выбраны два приоритета одновременно. `exclusive_scope` оставлен `multi: false`: ТЗ и journey расходятся (checkbox vs radio), выбрали то, что логичнее по смыслу опций (территория/сегмент — взаимоисключающие). Если автор ТЗ настаивает на checkbox — поправить одну строку.

**2. ✅ Исправлено — лимит «не более 4 элементов на вопрос» (FR-06, §7.2, §18.2).** У `proof`, `partner_wants`, `exclusive_scope` (PARTNERSHIP), `no_deal` (SALE), `known` (MARKET), `limits` (GENERIC) убрано по одному из трёх готовых вариантов — теперь 2 варианта + «Пока неизвестно» + своё поле = 4. `buildAnswer`/`buildPartnershipAnswer` проверены — убранные id (`economics`, `revenue`, `all`, `grow`, `nothing`, `time`) нигде в логике не читались, функциональность не пострадала.

**3. ✅ Исправлено — секции «Риски» и «Рекомендация» открыты по умолчанию.** `AdvisorAnswer.tsx`: добавлен `defaultOpen` на обе секции — теперь видны без разворачивания, как требует §18.3.

**4. ✅ Частично исправлено — битая ссылка на источник убрана.** «Открыть кейс в рабочем столе» (вела на `card_001` — карточку про риск-менеджмент, не связанную с Dr. John's) — удалена. Настоящей замены нет: в `mockCards.ts` нет карточки, соответствующей `case_dr_johns`. Если нужна рабочая ссылка — придётся завести такую карточку.

**5. ✅ Исправлено — follow-up пересчитывает вывод, а не только текст в чате.** Добавлен `FollowUpFlags` (`volumeGuaranteed`, `exclusivityLimited`) в `advisor.ts`. `buildFollowUpReply` теперь возвращает `{ text, flags }`; `AdvisorFlow.tsx` хранит `followUpFlags` в стейте и передаёт их третьим аргументом в `buildAnswer`. Проверено вживую: «гарантированный объём» убирает соответствующий риск из списка, «эксклюзивность на сегмент» снижает риск сценария «Эксклюзивное партнёрство» с «Высокий» до «Средний» в таблице сценариев. Категории follow-up про «сценарий/окно» и «риск» по-прежнему только текстовые — в примерах ТЗ (§17) они не меняют вывод, только поясняют его.

**6. ⚠️ Частично сделано — §30-31 ТЗ.** Добавлены рабочие кнопки «Подготовить вопросы партнёру» (`buildNegotiationQuestions`, сгруппированные вопросы по типу дилеммы) и «Сделать версию для акционера» (`buildShareholderSummary`, с копированием в буфер). §32-33 (сохранение сессии, «отправить коллегам», «вернуться после переговоров») **не сделаны** — это отдельная фича (персистентность + экран возврата к сессии), а не точечный фикс; проще и безопаснее делать отдельным заходом, а не приклеивать к этому набору правок.

**7. ⚠️ Частично сделано — честный поиск вместо притянутого текста (§9, FR-11).** `buildAnswer` теперь диспетчер по типу дилеммы: `partnership`/`build_or_partner` — существующая ветка; `sale` — новая бespoke-ветка (кейс Dr. John's реально рассматривал продажу бизнеса как один из вариантов, поэтому переиспользован осмысленно, не притянут за уши); `new_market`/`scaling`/`investment`/`org_model` — честная «слабая аналогия» с `evidenceLevel: "недостаточно данных"` вместо прежнего партнёрского текста не по теме. Это не решает FR-11 (в базе по-прежнему один кейс, реального retrieval нет), но останавливает главный побочный эффект — рекомендацию про «партнёра» и «долю» для вопроса про оргмодель или выход на рынок. Полноценное решение требует either нескольких размеченных кейсов + heuristic-подбора, either реального LLM+RAG (см. карту интеграции LLM выше).
