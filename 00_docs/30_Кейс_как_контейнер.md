# Кейс как контейнер файлов по теме (мини-спека)

Навигация: [[29_Ноутбуки_и_перетекание_знаний]] | [[02_О_чем_проект]] | [[06_Модель_данных]]

Дата: 2026-06-17 | Статус: на согласование

## Решение

**Кейс = скоуп файлов, объединённых одной темой** (а не «1 файл = 1 кейс», как сейчас по факту).
Это возвращает изначальный «кейс-контейнер» из доков, который в реализации схлопнули.

## Текущее состояние (что есть в коде)

- У документа уже есть поле `topic_ids` (фронт `Material`, бэк `documents.py:42`), но оно **захардкожено пустым** (`topic_ids=[]`, `documents.py:82`).
- Есть мок-роут `DELETE /topics/{topic_id}/documents/{id}` — то есть «тема как контейнер» уже заложена в API, но не используется.
- Вкладка «Кейсы» сейчас рендерит документы как карточки 1:1.
- Ask: `/documents/{id}/ask` (по документу, реальный) и `/api/v1/ask` (глобальный, реальный).

Вывод: **схема под контейнер наполовину готова, не достроено использование.**

## Целевая модель

```
Кейс (Topic)                 Документ (File)
  id                           document_id
  title (тема)                 original_name
  summary (агрегат, опц.)      topic_ids: [case_id, ...]   ← связь N:M
  file_ids: [...]              cardSummary (по файлу)
```

- Документ принадлежит 0+ кейсам (через `topic_ids`).
- Кейс агрегирует свои файлы (+ опционально сводную карточку).

## Ключевые сценарии

1. **Список кейсов.** Вкладка «Кейсы» = список кейсов-тем (карточка кейса: тема, число файлов, краткое). Клик → детально.
2. **Детально по кейсу.** Список файлов кейса + сводка; из файла → текущая модалка чтения/Q&A.
3. **Новый материал → в кейс.** Загрузка файла спрашивает: в существующий кейс или «создать кейс». Файл ингестится, ему проставляется `topic_ids=[case_id]`.
4. **Ask по кейсу.** Вопрос к кейсу = ответ по всем файлам темы (scope = чанки документов кейса), с цитатами на конкретные файлы.

## Что фронт-онли, что требует бэка

| Кусок | Фронт-онли | Требует бэка (снять заморозку) |
|---|---|---|
| Список кейсов (UI) | ✅ рендер из эндпоинта | мок отдаёт группировку (✅ в `mocks.py`) либо реально из тем |
| Группировка файлов по теме | ✅ если `topic_ids` приходят | **наполнение `topic_ids`** (сейчас `[]`) — реальный хэндлер |
| Детально по кейсу (файлы) | ✅ | — |
| Загрузка «в кейс» (UI выбора) | ✅ форма | **присвоение файла кейсу при ingestion** + персист — реальный хэндлер |
| Создание кейса | ✅ форма | **персист кейса** (таблица Topics) — реальный бэк |
| Ask по кейсу | частично | **topic-scoped retrieval** в `AnswerAgent` — реальный RAG |
| Карточка-сводка кейса | плейсхолдер | агрегат/LLM-сводка — реальный бэк |

## Фазирование (под текущую заморозку)

**Фаза 1 — РЕАЛИЗОВАНА (фронтовый слой над реальными документами, без бэк-моков):**
- Кейсы — фронтовый стор `stores/cases.ts`, членство персистится в **localStorage** (`bi_cases`). Кейсы настоящие (созданы юзером), файлы настоящие (реальные документы), членство настоящее. 1:N.
- `CasesBar` над сеткой «Кейсов»: «Все материалы» + кейсы-темы + создание кейса (inline-ввод). Выбор кейса фильтрует существующую сетку материалов (переиспользование, не вторая иерархия).
- **Дозагрузка файлов** (забыл/много): list-view → мультивыбор (чекбоксы) → `BulkActionBar` → «В кейс» → выбрать кейс. Работает в любой момент, не только при создании.
- Почему localStorage, а не мок-эндпоинты: честнее (реальные доки/членство), и не плодит «фейковые данные» в API.
- Ask по кейсу — **не в Фазе 1** (Фаза 2): требует topic-scoped retrieval. Пока кейс — это организация/фильтр файлов.

Открытые хвосты Фазы 1 (быстрые follow-ups): rename/delete кейса в UI; выбор кейса прямо в форме загрузки; перенос членства на бэк (Фаза 2).

**Фаза 2 — требует снятия заморозки бэка:**
- `topic_ids` реально проставляются при ingestion (файл → кейс), персист в БД (таблица Topics).
- `AnswerAgent` умеет scope по теме (retrieval по чанкам документов кейса) → настоящий ask-по-кейсу с цитатами.
- Сводная карточка кейса (агрегат/LLM).

## Миграция данных

Текущие документы — это «кейсы-одиночки». При переходе: каждый существующий документ → кейс из одного файла (или сгруппировать по эвристике темы позже). Ломать ничего не нужно — `topic_ids` пустой просто значит «кейс из одного файла».

## Открытые вопросы

1. Может ли файл быть в нескольких кейсах (N:M), или строго в одном (1:N)? (Спека заложила N:M; для MVP проще 1:N.)
2. Кто создаёт кейс-тему: пользователь при загрузке, или автогруппировка по темам при ingestion?
3. Ask-по-кейсу в Фазе 1: глобальный fallback или последовательный per-file — что честнее для демо?

## Связь с цифровыми двойниками (v-next)

Если двойник скоупит знания — он логично скоупится на кейсы/темы. То есть эта модель — фундамент и для двойников. Двойники остаются v-next (см. обсуждение).
